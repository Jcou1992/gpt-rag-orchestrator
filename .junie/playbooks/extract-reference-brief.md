# Playbook: Extract Reference Brief

**Purpose:** Inspect the *current* project (a reference codebase) and produce a `REFERENCE_BRIEF.md` that captures its stack, versions, conventions, and standards. The brief is then copied into the target project (the one being scaffolded) so the scaffolder can stay consistent.

**Run this playbook inside the reference project, not the target project.**

---

## Step 1 — Confirm context

Ask the user, in a single message:

1. Is this the project I should use as the reference? (Show detected project name from `package.json` / `build.gradle.kts` / `pom.xml` / `pyproject.toml`.)
2. Which parts matter most for consistency? Offer checkboxes:
   - Frontend (Vue components, composables, styling, state)
   - Backend (controllers, services, security, config)
   - Tooling (lint/format/test/CI)
   - Domain conventions (DTO naming, error envelopes, logging)
   - All of the above (default)

Wait for answer before continuing.

## Step 2 — Inspect

Only read files. Do not modify. Collect:

### Frontend signals (if a JS/TS project is present)
- `package.json` — all deps + versions, scripts, `engines.node`, package manager hint (`packageManager`, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`).
- `vite.config.*`, `vue.config.*`, `tsconfig*.json`.
- `.eslintrc*`, `eslint.config.*`, `.prettierrc*`, `.editorconfig`.
- Component structure: 3–5 representative `.vue` files. Note SFC style (Composition API `<script setup>` vs Options), `lang="ts"` presence, naming (PascalCase vs kebab), folder layout under `src/`. Flag whether the project is plain JS, TS, or mixed.
- State management (`pinia`, `vuex`, custom composables) — actual usage, not just dependency presence.
- HTTP layer (`axios`, `fetch`, wrapper location, error handling pattern).
- Styling approach (Vuetify theme tokens, SCSS, CSS vars, Tailwind).
- Test setup (`vitest`, `jest`, `@vue/test-utils`, `playwright`, `cypress`) + example test file shape.

### Backend signals (if a JVM project is present)
- `build.gradle.kts` / `pom.xml` — Kotlin/Java version, Spring Boot version, all deps + versions.
- `application.yml` / `application.properties` — config style (profiles, `@ConfigurationProperties` usage).
- Package layout under `src/main/kotlin|java/...`.
- Controller style (MVC vs WebFlux, DTO naming, validation annotations).
- Security config (OAuth2 resource server? custom filter? JWT decoder source).
- Error handling (`@ControllerAdvice`, problem-details RFC 7807, custom envelope).
- Test setup (`spring-boot-starter-test`, `MockMvc` vs `WebTestClient`, Testcontainers).

### Cross-cutting
- Git hooks (`.husky/`, `lefthook.yml`, `pre-commit`).
- CI (`.github/workflows/*`, `azure-pipelines.yml`).
- Monorepo markers (`pnpm-workspace.yaml`, `nx.json`, `turbo.json`).
- `.nvmrc`, `.tool-versions`, `.sdkmanrc`.
- `README.md` — any stated conventions.

## Step 4 — Hand off

Print to the user:
1. The absolute path of the written `REFERENCE_BRIEF.md`.
2. Instruction: `cp <path>/REFERENCE_BRIEF.md <target-project>/REFERENCE_BRIEF.md && cd <target-project>` then invoke `create-rag-app.md`.
3. A 5-line summary of the most load-bearing standards you captured.

Do not modify any other file in the reference project.
